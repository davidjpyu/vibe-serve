### Task
Add continuous batching to the decode loop and stream tokens per step to clients. Right now `main.py` serializes requests behind an `asyncio.Lock` and emits one big SSE frame after the whole generation; both must change.

**Architecture to build**

1. **Per-slot cache pool sized for B = `MAX_BATCH` concurrent sequences.** Pick `MAX_BATCH ≥ 16`; size each KV slot for a max-context length that comfortably covers the benchmark (default `MAX_MODEL_LEN=4096` is enough — the longest accuracy-checker prompt is well under that and the benchmark's `--max-tokens` defaults to 128). Pre-allocate once at server startup:
   - For each of the 8 full-attention layers: a single `(MAX_BATCH, num_kv_heads=4, MAX_MODEL_LEN, head_dim=256)` K buffer and matching V buffer, plus a `lengths: LongTensor[MAX_BATCH]` counter on device.
   - For each of the 24 GDN linear-attention layers: `(MAX_BATCH, num_v_heads=32, key_head_dim=128, val_head_dim=128) fp32` recurrent state and `(MAX_BATCH, conv_dim, kernel-1=3) fp16` conv state.
   - Slot manager owns a free-list of slot indices, plus an `active_slots: list[int]` representing the current batch composition.

2. **Async step engine**: one long-running `asyncio.Task` (call it `run_loop`) owns the GPU. It maintains:
   - `waiting: deque[Request]` — newly arrived requests awaiting prefill.
   - `active: dict[slot_idx -> Request]` — currently decoding.
   Each Request carries `prompt_ids`, `max_tokens`, `temperature` (treat ≤0 as greedy this round), `tokens_emitted`, a `done: asyncio.Event`, and a per-request `out_queue: asyncio.Queue[(token_id|None, finish_reason|None)]` consumed by the SSE handler.
   The loop alternates:
     a. **Admit phase** — while `len(active) < MAX_BATCH` and `waiting` is non-empty, pop a request, run prefill for it on a free slot, push its first decoded token into its `out_queue`, add it to `active`.
     b. **Decode phase** — if `active`: run one batched decode step for all active slots, distribute each row's new token into the corresponding `out_queue`. Mark any row that hit EOS (id=248044) or reached `max_tokens` as done (`finish_reason` `"stop"` or `"length"`), free its slot, signal `done`.
   If both `active` and `waiting` are empty, `await` on a `wake` event the request handler sets when a new request arrives.

3. **Batched decode primitives** — extend `VibeServeModel`'s per-layer modules so the decode step takes a batch `(B, 1, hidden)` tensor and a list of `slot_idx` (or a `slot_idx: LongTensor[B]` on device):
   - Full-attention: gather K/V from each layer's pool at the given slot indices (use `torch.index_select` or maintain the active set in a contiguous prefix — see below). Compute attention per row over its own `lengths[slot]` prefix. The simplest correct path is to keep `active_slots` in a contiguous prefix `[0..B_active)` of every layer's pool — when a slot finishes, swap-pop with the last active slot and update both the pool indices and the `lengths` tensor. This avoids gather/scatter on every step.
   - GDN: `fla.ops.gated_delta_rule.fused_recurrent_gated_delta_rule` already accepts batched `(B, num_heads, key_head_dim, val_head_dim)` recurrent state and `(B, conv_dim, kernel-1)` conv state — pass the contiguous active prefix of each pool. Make sure `initial_state` is the in-place storage so the kernel can update it (FLA returns a final_state; copy_ it back into the pool slot, or pass `output_final_state=True, use_cache=True` and let it write in place if supported — verify in the FLA source under `fla/ops/gated_delta_rule/`).
   - Embedding + LM head + RMSNorm work on `(B, 1, hidden)` unchanged.
   - The conv-1d step on GDN layers must consume the `(B, conv_dim, kernel-1)` state and the new input column, produce a new output column, and shift the state in place — same logic as R1's `_conv_update_step` but on the batched contiguous prefix.

4. **Prefill in the same engine**: for round 2 keep prefill simple — when admitting a new request, run prefill **alone for that single request** on its assigned slot (no batched prefill). This keeps complexity bounded; the decode batch is what wins throughput. Prefill fills slot K/V rows `[0, prompt_len)`, primes the GDN state via `chunk_gated_delta_rule`, and produces the first generated token.

5. **HTTP layer** — `POST /v1/completions` (and only that endpoint this round) still accepts `{prompt, max_tokens, temperature, stream}` and follows `serving-systems/references/tooling/openai-api.md`. The handler tokenizes the prompt, constructs a Request, registers it with the engine (`engine.submit(request)`), then:
   - If `stream=True`, returns a `StreamingResponse` that loops `await request.out_queue.get()`. For each token, decode it incrementally (use `tokenizer.decode([tok], skip_special_tokens=True)` plus a running offset or `tokenizers`'s `decode_step`); emit an SSE frame `data: {OpenAI completion chunk with that text}\n\n`. When the engine signals done, emit the terminal frame with `finish_reason` and then `data: [DONE]\n\n`. Per-token SSE frames are required — DO NOT buffer the whole generation.
   - If `stream=False`, accumulate tokens, return one JSON `text_completion` object.
   Keep the `/health` and `/v1/models` endpoints exactly as they were in R1.
   The asyncio.Lock that serialized R1's `/v1/completions` handler is GONE.

6. **Accuracy preservation** — the accuracy checker calls `VibeServeModel.from_pretrained(...).generate(input_ids, max_new_tokens=N)` directly (no HTTP). Keep `.generate()` working at batch=1 by routing it through the same step engine internally (submit a synthetic Request, drain its queue, return the prompt + emitted tokens as a LongTensor), OR by keeping the R1 single-stream `.generate()` path side-by-side. Either way, **14/14 EXACT-match against HF reference fp16 greedy must still pass**.
