### Bottlenecks
Ranked by impact (decode step wall = ~32 ms / 1,468 kernels / 18% GPU utilization): **1) Kernel-launch overhead is THE dominant bottleneck** — nsys cpu-overhead reports *LAUNCH-BOUND* with CPU launch 5.4 µs vs GPU exec 1.7 µs (3.17×). 988k matched launches, 1,468 kernels/decode-step, 26.3 ms of intra-step gap vs 5.7 ms of actual GPU compute → ~82% of every decode step is the GPU waiting for the next kernel to be enqueued. CUDA Graphs / torch.compile(mode='reduce-overhead') would collapse this. **2) No CUDA graphs active** (graph-replays returned empty) — the easiest single 2–4× decode win on a launch-bound workload. **3) cuBLAS GEMM kernels collectively dominate compute** (sum of 5 top nvjet_sm90 variants = 28.3+13.2+10.0+4.5+3.4 ≈ 59.4% of GPU busy time, mostly 30 µs/call). These are q/k/v/o/gate/up/down projections at decode batch=1, where the matmul is ridiculously short and FLOP-poor — a fused decode kernel (FlashAttention's `flash_attn_with_kvcache`) absorbs q/k/v into the attention call. **4) Pointwise / reduce kernel storm** (elementwise + vectorized_elementwise + reduce + splitKreduce + unrolled_elementwise + softmax_warp = 11.3+14.4+3.8+3.5+3.2+0.6 ≈ 36.8% of GPU compute, ~860k separate launches). These are all candidates for fusion via torch.compile or hand-fused RMSNorm/RoPE/SwiGLU kernels. **5) CatArrayBatchedCopy on the hot path** — 36,928 calls = exactly once per layer per token, confirming `_rotate_half`'s `torch.cat` runs every decode step. 65.5 ms of cumulative GPU time + the extra launch overhead. Replace with a rotate-half formulation that doesn't allocate (e.g. `torch.stack(...).reshape(...)` or precompute a permuted cos/sin). **6) SDPA[MATH] decode attention** — even though softmax_warp is only 0.6% and the per-head GEMMs are bundled into nvjet_sm90_hsh_64x8 (4.5%), the MATH path materializes the (1×L) attention matrix and runs full softmax → reduce. FlashAttention single-kernel would cut both the GEMM and softmax to one launch per layer (~50 µs total/decode-step instead of ~3 ms). **7) asyncio.Lock serialization** (already known from benchmark: TTFT P99 22.4s, request_throughput = single-stream-rate). 9 idle-gap windows of 10–11 ms between requests confirm the server is fully request-serialized; batching unlocks parallel throughput. **NOT bottlenecks**: cudaStreamSynchronize (132 ms / 0.5% of CPU time over 1,154 calls — the per-token .item() costs are negligible); H↔D memcpy (9 µs total over the window); no memory thrash; lm_head/embed (tiny).

### Suggestions
Highest-ROI first, tied to specific nsys evidence: **A) CUDA Graphs on the decode path** (addresses bottlenecks #1, #2, #4). The profile is unambiguous: 1,468 kernels/step, 5.4 µs CPU launch vs 1.7 µs GPU exec, 82% of step wall is gap. Two options — (a) capture `_forward_inner(next_tok, cache_start=…)` once per (bsz, cache_count_bucket) with `torch.cuda.CUDAGraph().capture_begin()/replay()`, advancing cache_count via a device-side counter; or (b) wrap the inner forward with `torch.compile(model, mode='reduce-overhead', fullgraph=True)` which does CUDAGraphs + kernel fusion automatically. Expected: decode TPOT drops from 27→8–12 ms (2–3× tok/s for a single stream) just by deleting launch overhead. **B) FlashAttention v2/v3 (or `flash_attn_with_kvcache`)** (bottleneck #6) — H200/SM9.0 has the fast kernels. Removes the `with sdpa_kernel([SDPBackend.MATH])` block at line 195 of main.py (keep it gated behind an env var so acc_checker can still pin MATH). One-kernel-per-layer instead of GEMM+softmax+GEMM. **C) Replace `_rotate_half`'s `torch.cat`** (bottleneck #5) — 36,928 CatArrayBatchedCopy launches/window. Rewrite as either: a complex-number multiply with cos+1j·sin precomputed; or, simpler, change the cos/sin layout so RoPE is one mul + one add of in-place views. Eliminates ~37k CUDA launches per window. **D) Continuous / dynamic batching** (bottleneck #7) — coalesce decode forward passes across in-flight requests so 9 idle-gap windows of 10–11 ms disappear and decode bsz scales linearly. GPU compute at bsz=1 is so under-utilized (the GEMMs run at 30 µs each — completely memory-bandwidth-bound at bsz=1) that growing to bsz=8 or 16 will scarcely move per-step latency but multiplies throughput. The H200 has 143 GB free of 143 GB; ample KV-cache headroom for >32 concurrent 4k-context requests. **E) Fused RMSNorm and fused SwiGLU MLP** (bottleneck #4) — RMSNorm is currently 5+ pointwise launches × 2 norms × 32 layers per step. Substitute Apex/FlashInfer's fused RMSNorm or compile-time fuse via torch.compile to collapse to 1 launch each. SwiGLU MLP (gate * silu(up) then down) is 4-5 launches/layer; fuse to 1-2. Reduces the `elementwise_kernel`/`vectorized_elementwise_kernel` storm (currently 14.4+11.3 = 25.7% of GPU compute over 688k launches). **F) Stack per-layer KV caches into one (num_layers, 1, num_kv_heads, max_seq, head_dim) tensor** — removes 32 Python dict lookups per step and is also a paged-attention prerequisite. **G) Token tape on device** — keep generated ids in a CUDA tensor; only sync on EOS detection. Necessary precursor to (A) because CUDAGraph capture cannot tolerate `.item()` inside the replay. **H) BF16 over FP16** — Hopper FP16 vs BF16 perf is near-equal but BF16 sometimes wins on cuBLAS path selection; cheap to try. **Suggested execution order**: G → A → B → D → E → C → F → H. After A alone, decode TPOT should approach ~10 ms (3× tok/s for single stream). A+B+D together should hit 200–400+ tok/s aggregate at concurrency 8.

## Round 2 — Orchestrator (plan)
- **reasoning**: Round 1 baseline shipped clean (acc 14/14, 36.38 tok/s, both endpoints streaming). The profile is unambiguous about the structural problem: requests are serialized by an asyncio.Lock, so aggregate tok/s ≈ single-stream tok/s no matter how much we improve the per-step path. The optimization floor demands continuous batching first; the benchmark's Poisson arrival pattern makes this the single biggest aggregate-tok/s lever (4-10× expected). Doing CB first also forces the KV cache and scheduler into the shapes that FlashAttention's varlen-decode (M4) and CUDA-graph bucketing (M5) want anyway — order matters; CUDA graphs first would have to be redone at batch>1 a round later. Scoped to the scheduler + batched-attention plumbing only; keeping SDPA[MATH] preserves the accuracy gate so we can land the structural change cleanly before touching the kernel.

### Task
Add continuous batching to `main.py` so decode steps coalesce across in-flight requests. Today every `/v1/completions` / `/v1/chat/completions` call grabs a global `asyncio.Lock` and runs prefill + 128 decode steps to completion before the next request even starts — TTFT P99 was 22.35s in the round-1 benchmark and there are 9 idle-gap windows of 10-11 ms between requests in the profile. Replace this with a single background scheduler that maintains a pool of decode slots and runs one batched decode step per scheduler tick across all active slots.

Concrete design (the implementer may adjust details but must hit the externally-visible behavior below):

1. **Slot pool.** Reallocate the per-layer KV caches from shape `(1, num_kv_heads, max_cache_len, head_dim)` to `(N_SLOTS, num_kv_heads, max_cache_len, head_dim)` (e.g. N_SLOTS=16; pick something that fits H200 memory comfortably — at 4096 ctx, 32 layers, 8 KV heads, head_dim=128, fp16 = ~2 GiB per slot pair, so 16 slots ≈ 32 GiB, well under the 143 GB available). Each in-flight request owns one slot for its lifetime; on completion the slot is returned to a free list.

2. **Scheduler loop.** One asyncio task (or dedicated thread) is the *sole* GPU consumer. Each tick: (a) admit up to K newly-arrived requests from a wait queue — for each, assign a free slot and run prefill into that slot's KV at position 0..prompt_len (prefill may be done one-at-a-time this round; do not block decode on a long prefill train — a single prefill per tick is fine); (b) gather all active slots' next-decode positions into a `(B,)` LongTensor of cache lengths and a `(B, 1)` next-token tensor; (c) run one batched `_forward_inner` decode call that writes K/V at each slot's current position and produces `(B, vocab)` logits; (d) argmax → `(B,)` next tokens; (e) for each slot, push the token onto that request's `asyncio.Queue` (the streaming endpoint reads from it), bump its position, and free the slot if EOS (128001/128008/128009) is produced or `max_tokens` reached.

3. **Batched attention with variable cache lengths.** Different slots will be at different positions. Two acceptable implementations: (i) pad the K/V to the max cache length in the batch and supply a `(B, 1, 1, max_len)` additive attn_mask that puts `-inf` on positions ≥ each row's cache length, then call SDPA with `enable_gqa=True` and `is_causal=False`; or (ii) gather only the live prefix per row into a `(B, num_kv_heads, max_len_in_batch, head_dim)` working buffer per layer and mask the same way. Keep the SDPA[MATH] backend for now so accuracy still matches HF eager. **Greedy decoding must remain bit-identical to single-stream**: a slot's next token must not depend on what other slots are doing in the batch. Padding-with-mask gives this if and only if the mask correctly zeros out attention to padding positions for every row.

4. **Endpoints unchanged externally.** `POST /v1/completions` and `POST /v1/chat/completions` still take their existing request shape, still stream SSE with the same `text_completion` / `chat.completion.chunk` frames and `data: [DONE]` terminator, still respect `max_tokens` and the three EOS ids, still return `finish_reason`. The change is purely internal: the per-request handler enqueues a job into the scheduler's wait queue, then drains tokens from its per-request `asyncio.Queue` to emit SSE frames.
